# PawConnect – Agent Brief

Read this whole file before doing anything in this repository. It is shared by Claude Code (via CLAUDE.md) and Codex.

## 1. What this project is

- PawConnect is a **prototype** pet adoption web platform built by a 5-person university team (USYD PMGT5871 Project Planning, Group Assignment 2) using Scrum and Jira.
- The assignment assesses how the team applies **Scrum**. The website is **not assessed for design, complexity or technical quality**; it proves that each user story marked Done in Jira was really delivered.
- A story counts as Done only if it is Done in Jira **and** a screenshot of the working feature appears in that sprint's review evidence. Every feature must genuinely work against the shared (fictional) database. Never fake a feature with hard-coded output.
- Users: **Prospective Adopter** (browses, no login), **Applicant** (has submitted an application, no login), **Shelter Staff** (uses one shared demo staff login).
- Vision: adopters discover suitable pets, submit applications and track progress; shelters manage pets and applications in one place.

## 2. Rules for the coding agent

1. **Build only the story named in the prompt.** Each prompt names one Jira story (key such as `PPAP-13`, internal ID such as `E03`) and pastes its acceptance criteria. Do not implement other stories, even small ones, and do not "improve" other pages. Building ahead breaks the team's sprint evidence.
2. **Meet every acceptance criterion exactly as written.** If an AC is ambiguous, conflicts with this file, or seems to need another story first, **stop and ask** instead of guessing.
3. **Keep it simple.** Plain HTML + CSS + vanilla JavaScript (ES modules). No framework, no bundler, no build step. Clean, minimal styling. Pages should stay usable at mobile width (shared CSS), but responsive design is not a separate story.
4. **Shared files need care.** `css/style.css`, `js/supabase.js`, `js/nav.js` and `config.js` are used by everyone. Change them only when the story needs it, keep changes small, and say so in your summary.
5. **One story = one small change set.** Suggest a commit message: `PPAP-<n> <internal ID> <short summary>`, e.g. `PPAP-13 E03 Add staff application list`.
6. **Finish with a manual test list**: for each AC, the click path and the expected result, so a teammate can cross-test and screenshot it.
7. **Fictional data only.** Never add real names, phone numbers, emails or addresses. Use `example.com` emails.
8. **Database changes** go in a new file `supabase/migrations/NNN_description.sql` (start at `002_`), with the Jira key in a comment at the top. Say clearly that a human must run it in the Supabase SQL Editor. Never edit `supabase/schema.sql` for a story, and never assume a change exists until the human confirms it was run.
9. **Secrets:** the Supabase anon / publishable key may live in `config.js` (it is public by design; Row Level Security protects data). The **service_role / secret key must never** appear in the repo or front-end code.
10. Use **relative links only** (no leading `/`): the site is served from `/pawconnect/` on GitHub Pages.
11. UI text in English (Australian spelling).

## 4. Data model (see `supabase/schema.sql`)

- `shelters(shelter_id, shelter_name, area, description)`
- `pets(pet_id, shelter_id, name, animal_type, breed, age, age_group, photo, description, temperament, adoption_requirements, availability)`
  - `animal_type`: Dog | Cat | Rabbit | Other
  - `age` in years. `age_group` is generated by the database but **no story uses it** (C05 became keyword search); do not build features on it
  - `availability`: **Available | Unavailable** (changed manually by staff; never changed automatically by application status)
  - `photo` is an image URL
- `applications(application_id, pet_id, applicant_demo_name, demo_contact, reason, application_status, submitted_at)`
  - `application_id` is generated by the database: `APP-1001`, `APP-1002`, … (seed data uses 1001–1003)
  - `application_status`: Pending | Under Review | Approved | Rejected; **new applications are always Pending**

Access rules (enforced in the database):

- Public (anon) can **read** shelters and pets.
- Public **cannot read or edit `applications` directly**. They use:
  - `rpc('submit_application', { p_pet_id, p_name, p_contact, p_reason })` → returns the new `application_id`; rejects missing fields and pets that are not Available.
  - `rpc('track_application', { p_application_id })` → returns at most one row: `application_id, pet_id, pet_name, application_status, submitted_at` (no personal details); zero rows means not found.
- Signed-in staff (`authenticated`) can read and update applications, and insert / update pets. Because of this, **staff pages must sign in** with the staff demo account before they can load data. This is a technical requirement of the prototype, not the future adopter account feature (A05).

## 6. Definition of Done (code side)

A story is ready for the team's **Testing** column when every AC works against live Supabase data on the deployed GitHub Pages site, there are no console errors on the affected pages, and the manual test list is written. It moves to **Done** only after a teammate (not the developer) has cross-tested it and the screenshot evidence is saved.
